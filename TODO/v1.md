# Make Codex threads readable from any agent

## Problem

Codex stores local thread history, but agents do not always receive the native
thread read tools. An agent may have a Codex thread ID or deep link and still
have no stable way to inspect that thread.

`codex-thread` will provide one read-only CLI for local Codex threads. It will
use the existing Codex CLI and return stable output designed for agents.

## V1 outcome

An agent can:

- list local Codex threads
- find threads by title
- read a thread from a Codex deep link or thread ID
- select one turn or a recent window of turns
- consume versioned JSON or chronological JSONL
- diagnose a missing or incompatible Codex installation
- install the bundled `codex-thread` skill

## Boundaries

V1 will:

- use the existing `codex` executable as a prerequisite
- start a short-lived `codex app-server` process over stdio
- use the standard Codex home and environment behavior
- call read-only app-server methods
- normalize app-server responses into package-owned schemas
- support active and archived thread metadata where the app-server exposes it

V1 will not:

- bundle `@openai/codex`
- know about T3 Code, T3 profiles, or T3 storage
- discover alternate Codex homes
- parse Codex SQLite databases or rollout files directly
- resume, fork, rename, archive, delete, or modify a thread
- promise complete output for a thread that is still active
- depend on experimental app-server methods
- tail live threads or build subagent hierarchy

The child process inherits the caller's environment. A caller that already sets
`CODEX_HOME` keeps standard Codex behavior, but v1 adds no home selection or
profile discovery of its own.

## CLI contract

Commands:

```text
codex-thread list
codex-thread find --title <text>
codex-thread get <thread-reference>
codex-thread doctor
codex-thread schema <schema-name>
codex-thread install --skills codex
```

`get` accepts:

- `codex://threads/<thread-id>`
- a path-safe Codex thread ID

Title lookup stays in `find`. The CLI never treats an unknown ID as a title and
never chooses one result from an ambiguous search.

Shared options:

```text
--format human|json|jsonl
--help
--version
```

List options:

```text
--limit <count>
--offset <count>
--reverse
--archived
--include-subagents
```

Find options:

```text
--reverse
--archived
--include-subagents
```

`find` matches title text as a trimmed, case-insensitive substring. It searches
metadata only and never searches message content. The implementation will page
through app-server results as needed so search behavior does not depend on the
server's case-sensitive `searchTerm` behavior. Like `t3-thread find`, it returns
every title match without `--limit` or `--offset`.

Get options:

```text
--last-turn
--turn <turn-id>
--turn-limit <count>
--turn-offset <count>
```

The turn options follow the `t3-thread` rules:

- `--turn` cannot be combined with any turn-window option
- `--last-turn` cannot be combined with `--turn-limit` or `--turn-offset`
- selections count from the newest turn and emit in chronological order
- an exact missing turn emits `TURN_NOT_FOUND` and exits 2
- a turn window past the end is a valid empty page and exits 0
- every bounded response carries a `selection` object

V1 will call stable `thread/read` with `includeTurns: true` and apply turn
selection locally. It will not require the experimental turn pagination API.

## App-server transport

Each storage command will:

1. resolve `codex` from `PATH`
2. spawn `codex app-server` without a shell
3. send `initialize`
4. send the `initialized` notification
5. call the required read method
6. collect the response for that request ID
7. close stdin and wait for the child to exit

The transport must:

- use argument arrays and JSON serialization
- keep protocol data off stderr
- ignore unrelated notifications while waiting for a response
- reject malformed JSON and duplicate response IDs
- enforce startup, request, and shutdown timeouts
- report early process exits with captured diagnostics
- handle closed stdout without an unhandled error
- avoid logging environment values or authentication data

V1 will initialize without experimental capabilities. It will use:

- `thread/list` for listing and title search
- `thread/read` with `includeTurns: true` for retrieval

Listing will request all supported top-level Codex sources needed for CLI, IDE,
desktop, and app-server threads. Subagent source kinds stay hidden unless the
caller passes `--include-subagents`.

## Normalized data

The main thread envelope will use this shape:

```text
schemaVersion
toolVersion
thread
turns
messages
activities
runtime
warnings
selection
```

`selection` is omitted from a full read. Its presence always means the output is
partial history.

Messages contain normalized user and assistant content. Activities contain all
other Codex items, including commands, file changes, plans, tool calls, web
searches, and subagent activity. Unknown item types remain available through an
`adapterSpecific` object and produce a warning when data could not be mapped to
a stable field.

Null and unknown values remain explicit. The normalizer must not infer a title,
turn result, parent relationship, or completion state from timestamps.

If the latest returned turn is in progress, output will warn that the transcript
may still change. Runtime state reports the app-server observation and does not
claim access to another client's in-memory state.

## Schemas

Bundle these JSON schemas:

```text
thread.v1
list.v1
find.v1
jsonl-record.v1
doctor.v1
error.v1
```

Schema identifiers:

```text
codex-thread.thread.v1
codex-thread.list.v1
codex-thread.find.v1
codex-thread.jsonl-record.v1
codex-thread.doctor.v1
codex-thread.error.v1
```

JSONL starts with one header record, followed by normalized records in
chronological order. Consumers never need to sort records.

List and find output contains metadata only. It must not contain message,
activity, command, tool output, or instruction text.

## Errors and exit codes

Use one error shape on stderr:

```json
{
  "schemaVersion": "codex-thread.error.v1",
  "code": "INVALID_ARGUMENTS",
  "message": "limit must be a positive integer.",
  "details": {
    "field": "limit",
    "value": "0"
  }
}
```

Exit codes:

```text
0  success
1  unexpected failure
2  thread or exact turn not found
3  invalid arguments or install conflict
4  Codex executable or app-server unavailable
```

App-server protocol errors receive stable package error codes. Raw app-server
error text may appear in `details` when it contains no credential or private
conversation data.

## Doctor

`doctor` will check:

- Node version support
- whether `codex` resolves from `PATH`
- whether app-server starts
- whether initialization succeeds
- whether stable `thread/list` and `thread/read` methods are available
- detected Codex and package versions when exposed by the protocol

Doctor must not read or print transcript content. A failed report still emits a
complete `doctor.v1` envelope and exits with the matching nonzero code.

## Skill

The bundled skill will teach agents to:

1. check `codex-thread` and `codex` prerequisites
2. use `list` or `find` when no exact ID is available
3. confirm a result with `get ID --last-turn --format json`
4. treat every response with `selection` as partial history
5. use JSON for an envelope and JSONL for chronological records
6. preserve warnings and nonzero exit diagnostics
7. avoid full reads until the candidate is confirmed
8. report active-thread uncertainty

The skill will contain no T3-specific paths, commands, or assumptions.

## Critical automated test scope

The first suite covers only failures at the boundaries below.

A test belongs in the first suite only when a regression could:

- cross the read-only app-server boundary
- hang a command or silently corrupt, omit, or reorder thread history
- change a documented JSON, JSONL, warning, error, or exit-code contract
- expose transcript content during discovery or diagnostics
- replace user-edited skill files or write outside the selected skill directory

Do not use test count or line coverage as a target. Add a regression test when a
bug reaches one of these boundaries.

### Test harness

Use Node's built-in `node:test` runner and `node:assert/strict`. Keep the suite
offline and deterministic:

- inject a fake app-server process and fake client instead of starting a real
  authenticated Codex session
- use small raw thread fixtures that contain user messages, assistant messages,
  activities, unknown items, null fields, and more than one turn
- inject clocks and process behavior where timing or timestamps affect output
- use temporary directories with cleanup for skill installation tests
- validate machine envelopes and JSONL records against the bundled schemas
- keep fixtures free of real thread IDs, prompts, credentials, and home paths

### Required suites

#### App-server transport

- prove the full initialize, `initialized`, read request, response, and clean
  shutdown lifecycle over chunked stdio
- reject every method except `thread/list` and `thread/read` before spawning a
  process
- reject malformed or non-object JSON, unknown or duplicate response IDs, and
  responses missing both `result` and `error`
- prove startup, request, and shutdown timeouts settle without hanging
- prove early exits return bounded diagnostic metadata and a stable reason
  without returning raw stderr text

These tests protect the read-only boundary and prevent protocol failures from
becoming hangs or plausible but incomplete results.

#### Client discovery and retrieval

- collect multiple list pages, apply `limit` and `offset` locally, report
  `hasMore`, and reject a repeated cursor
- search every page with trimmed, case-insensitive title matching while keeping
  list and find results metadata-only
- request `includeTurns: true`, reject a wrong thread ID or malformed thread
  shape, and map missing-thread and paginated-history protocol errors to their
  public errors

These tests protect complete discovery and prevent the client from returning a
different or partially validated conversation.

#### Normalization and selection

- preserve the source order of mixed messages and activities through stable
  sequence values and JSONL output
- preserve unknown items under `adapterSpecific` with a warning and reject
  invalid declared field types or duplicate turn IDs
- distinguish an exact missing turn from a valid empty window and select recent
  turns in chronological order
- report active-thread and in-progress-turn warnings, including for bounded
  reads
- validate representative thread, list, and find envelopes against their
  bundled schemas

These tests protect transcript integrity and the partial-history contract.

#### Machine output and CLI

- prove JSONL emits one header followed by turns and their items in source order,
  with selection and warnings retained
- prove list and find JSON and JSONL never include message, activity, command,
  tool-output, or instruction text
- cover command dispatch with an injected client and the option combinations
  that can make a request ambiguous, including missing or negative values,
  duplicate options, unsupported options, and conflicting turn selectors
- prove invalid arguments, a missing exact turn, a missing thread, and an
  unavailable app-server produce the documented exit code and one JSON error on
  stderr without protocol output on stdout

These tests protect agent consumers that treat stdout and exit status as a
machine interface.

#### Doctor

- cover a healthy fake installation, a missing executable, initialization
  failure, stable-method failure, and the empty-list missing-thread probe
- prove every path returns a complete `doctor.v1` report with the correct exit
  code and no transcript content

These tests keep setup failures actionable without turning diagnostics into a
history read.

#### Skill installation and package contents

- install only into an isolated `CODEX_HOME`, refuse an existing destination
  without an explicit replacement policy, and preserve the old skill during
  backup
- reject symlinked parents and destinations while leaving an outside sentinel
  unchanged
- verify the package file allowlist, required release files, schema identifiers,
  bundled skill files, executable entry point, and public import

These tests protect user files and catch packages that would install without the
runtime contracts they expose.

### Deferred coverage

Do not add these tests unless a bug or new contract makes them necessary:

- full snapshots of human-readable output
- one test for every activity summary or optional metadata field
- direct tests of private helpers already exercised through a public boundary
- every equivalent parser permutation
- real Codex, network, authentication, or private-history integration tests in
  the default suite
- T3-specific SQLite, WAL, provider JSONL, tail, live-state, or participant tests
- broad operating-system matrices or performance tests

### Implementation order

1. Add the fake app-server and raw-thread fixtures.
2. Cover transport, client retrieval, normalization, selection, and machine
   output.
3. Cover CLI and doctor failure mapping.
4. Cover skill installation and package contents.
5. Run `npm test` and `npm run check`, then perform one manual smoke check with
   sanitized local thread data before publishing.

## Subagent use

Luna High subagents may be used for bounded implementation or review work when
parallel work helps. No more than two Luna High subagents may run at once. The
root agent owns integration and assigns non-overlapping files or read-only
reviews.

## Done

V1 is ready when an agent with only the `codex-thread` skill and shell access can
find a local Codex thread, confirm it with a bounded read, retrieve selected
turns, and consume stable JSON or JSONL without native thread tools.
