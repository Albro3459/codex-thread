# Follow Codex threads and expose subagents

## Problem

V1 can read a stored Codex thread once. An agent that needs updates must repeat
the command and compare full responses itself.

V1 also preserves Codex subagent activity, but callers must inspect raw activity
payloads, recover child thread IDs, and read each child separately. This makes a
common thread review harder than it should be.

## V2 outcome

V2 adds only two capabilities:

- follow a stored thread through change-oriented polling
- list its Codex subagents and show explicit parent relationships

Every V1 command and schema keeps its existing behavior.

## Boundaries

V2 will:

- poll stable `thread/read` responses without resuming the thread
- stream one baseline followed by new or changed records
- let callers bound a tail by cycles, time, or one observation
- let callers restrict each tail cycle to recent turns
- discover subagents from explicit Codex activity and thread metadata
- return subagent metadata without child transcript content
- build hierarchy only from explicit parent thread IDs
- add versioned tail and participant schemas
- update the bundled skill for both workflows

V2 will not:

- add thread mutation, resume, fork, archive, rename, delete, or rollback
- connect to or control an existing Codex, IDE, desktop, or T3 process
- read Codex databases, rollout files, T3 storage, or provider JSONL directly
- discover alternate Codex homes or T3 profiles
- use experimental `thread/turns/list`, `thread/items/list`, `parentThreadId`,
  or `ancestorThreadId` APIs
- add server-side turn pagination
- add message-content search
- emit deletion records from a tail
- infer parentage, completion, or live state from timestamps
- add unrelated CLI aliases, formats, filters, or package features

The [official Codex app-server documentation](https://learn.chatgpt.com/docs/app-server)
states that `thread/read` reads stored data without resuming or subscribing to a
thread. It also marks turn pagination and parent-thread list filters as
experimental. V2 will poll the stable read method and keep those experimental
methods out of the package.

## CLI contract

Add these commands:

```text
codex-thread tail THREAD [--once] [--interval MS] [--max-cycles N] [--timeout MS] [--turn-limit N]
codex-thread participants THREAD [--last-turn | --turn ID | --turn-limit N --turn-offset N]
```

Participant paging and hierarchy options:

```text
--limit N
--offset N
--reverse
--tree
```

V1 command syntax stays unchanged.

## Tail a thread

### Polling model

Each cycle will call stable `thread/read` with `includeTurns: true` through a
fresh, private app-server observation. The command will normalize the response,
apply `--turn-limit` locally, compare it with the prior cycle, and emit only
records that are new or changed.

`--turn-limit` bounds agent-facing output. The app-server still returns full
history internally because stable server-side turn pagination is unavailable.
Threads that reject a full-history read keep the existing
`UnsupportedHistoryError` behavior.

The tail observes persisted snapshots. It does not subscribe to the active
client and must not claim that a quiet cycle means the thread is finished.

### Lifecycle options

```text
--once             Read one cycle and stop
--interval MS      Milliseconds between cycles, default 1000
--max-cycles N     Stop after N attempted cycles
--timeout MS       Stop after the wall-clock limit
--turn-limit N     Keep only the newest N turns in each cycle
--format jsonl     Stream records as they are produced, default
--format json      Buffer records for a bounded tail
```

`--interval` must be between 100 and 60000 milliseconds. Counts and timeouts
must be positive integers.

`--once` cannot be combined with `--interval`, `--max-cycles`, or `--timeout`.
JSON output requires `--once`, `--max-cycles`, or `--timeout` because an
unbounded JSON document never finishes. Tail does not accept exact-turn or
turn-offset selection because those views cannot follow the newest work.

The bundled skill will always use a bounded tail. An unbounded JSONL tail is for
an interactive terminal where a person can interrupt it.

### Change records

Add `codex-thread.tail-record.v1`:

```text
schemaVersion
op
recordType
threadId
observedAt
cycle
data
```

Operations:

```text
upsert
runtime
end
```

Record types:

```text
thread
turn
message
activity
runtime
end
```

Cycle 1 emits a complete baseline for the selected window. Later cycles emit an
`upsert` only when a thread, turn, message, or activity is new or changed.
`upsert` means replace the record with the same stable identity. Consumers must
not append duplicate copies.

Records inside each cycle use the same chronological order as `get --format
jsonl`. An unchanged cycle emits no data records. A record that leaves a bounded
turn window and later returns may be emitted again as an upsert.

Turn IDs, message IDs, and activity IDs are the primary identities. A null item
ID uses a deterministic fallback made from its turn ID, item kind, and sequence.
Runtime comparison excludes `observedAt` so the clock alone cannot make every
cycle appear changed.

V2 does not report deletions. A record absent from a later cycle must not be
treated as deleted.

### Tail completion and errors

A successful tail emits exactly one `end` record with one of these reasons:

```text
once
max-cycles
timeout
interrupt
thread-not-found
```

The end record reports the number of attempted cycles. Reaching a bound says why
the command stopped. It does not say the thread completed.

A thread missing on the first cycle behaves like `get`: no stdout, one stable
error on stderr, and exit code 2. A thread that disappears after a successful
cycle emits `end` with `thread-not-found`, then exits 2.

SIGINT emits `end` with `interrupt`, flushes stdout, and exits cleanly. A closed
stdout stops quietly. Other app-server errors keep the existing error shape and
exit classification. V2 will not add a retry policy.

## Show thread participants

### Command behavior

`participants` answers which Codex subagent threads worked under one root
thread. It returns metadata and discovery evidence. It does not embed prompts,
messages, tool output, or child results.

Examples:

```bash
codex-thread participants THREAD --last-turn --format json
codex-thread participants THREAD --limit 20 --format json
codex-thread participants THREAD --tree --format json
```

Turn selection uses the V1 rules. A response with `selection` is partial. An
exact missing turn adds `TURN_NOT_FOUND` and exits 2. A turn window past the end
is a valid empty result.

Participants are ordered by first discovery, then by child thread ID. `--reverse`
reverses that order. `--limit` and `--offset` page the returned participants.
Counts are computed before paging so callers can detect truncation.

`--tree` is available for human and JSON output. JSONL stays flat and rejects
`--tree`.

### Discovery sources

V2 will combine these read-only sources:

1. Read the requested root thread and scan only `collabAgentToolCall` and
   `subAgentActivity` records.
2. Accept child IDs only from explicit `agentThreadId`, `receiverThreadIds`, or
   child metadata fields owned by those item types. A spawn record's sender and
   receiver IDs form an explicit relationship.
3. Page `thread/list` with subagent source kinds and keep summaries whose
   explicit `parentThreadId` belongs to the discovered tree.
4. Use `thread/read` with `includeTurns: false` to confirm and enrich a child
   referenced by activity but absent from the list.
5. Continue through explicit child relationships with a visited set so nested
   subagents can be represented without cycles or duplicate reads.

Activity references are the primary discovery source for direct children.
`thread/list --include-subagents` supplements them and helps discover deeper
relationships. A list omission must not erase a child that the parent explicitly
referenced. This covers the observed case where an older compacted T3-backed
thread exposed child IDs in activity but did not return them from the list.

The command never searches arbitrary strings for thread-like IDs. It never uses
timestamps, activity order, names, roles, or identifier shape to invent an edge.

### Participant envelope

Add `codex-thread.participants.v1`:

```text
schemaVersion
toolVersion
threadId
ordering
selection
counts
hierarchyAvailable
participants
warnings
```

Each participant contains:

```text
threadId
parentThreadId
path
depth
title
source
agentNickname
agentRole
model
reasoningEffort
status
state
agentPath
turnId
turnIds
firstSeenAt
lastSeenAt
activityCount
discoveredBy
```

Null values remain explicit. `discoveredBy` contains only activity identity and
kind, not prompt or result content.

`state` is `finished` only when Codex recorded a terminal child or activity
status. A non-terminal status maps to `running`. Missing status maps to
`unknown`. Silence and old timestamps never imply completion.

### Hierarchy

An edge is valid only when child metadata names the requested root or another
known participant as `parentThreadId`, or when a spawn record explicitly links
its sender and receiver thread IDs. Conflicting sources produce a warning and no
inferred edge.

`hierarchyAvailable` is true when at least one explicit parent edge resolves to
the root or another returned participant. It can be false on a valid flat result.

Paths use deterministic labels such as `main.subagent1.subagent1a`. Labels are
assigned only after an explicit edge resolves. `depth` is measured from the
requested root, which is represented by the synthetic `main` segment and is not
returned as a participant.

The default JSON result is flat. With `--tree`, roots appear in the top-level
array and descendants appear under `children`.

### Participant warnings

Use stable warnings for conditions a caller must preserve:

```text
CHILD_READ_FAILED
CHILD_NOT_IN_LIST
CONFLICTING_PARENT
UNRESOLVED_PARENT
PARENT_CYCLE
PARENT_OUT_OF_PAGE
PARENT_OUT_OF_SELECTION
```

A child referenced by parent activity remains in the result when its metadata
read fails. Unknown fields stay under `adapterSpecific` where useful. An empty
participant list is valid and exits 0.

## Machine output

Bundle these new schemas:

```text
tail-record.v1
participants.v1
```

Schema identifiers:

```text
codex-thread.tail-record.v1
codex-thread.participants.v1
```

Extend `jsonl-record.v1` with `participants` and `participant` record types.
Tail records keep their separate change-oriented schema.

Participant JSONL starts with one metadata header, followed by flat participant
records. Tail JSONL emits records as each cycle completes and never wraps them in
an array.

## Critical tests

Add tests only for the new contracts and their interaction with V1 boundaries.

### Tail tests

- emit the selected baseline in chronological order
- emit changed records once and omit unchanged records
- re-emit a record that changes in place
- keep `--turn-limit` bounded as the newest window moves
- ignore `runtime.observedAt` during change detection
- produce exactly one end record for each successful stop reason
- distinguish a missing startup thread from a thread that disappears later
- handle SIGINT and closed stdout without corrupting JSONL
- validate lifecycle option conflicts and bounded JSON output
- preserve V1 warnings, errors, and read-only method restrictions
- validate every emitted record against `tail-record.v1`

### Participant tests

- discover and deduplicate IDs from both Codex subagent activity types
- enrich listed children without reading child turns
- recover an activity-referenced child when list omits it
- preserve a child with a warning when its metadata read fails
- confirm parent links and reject conflicts, unresolved parents, and cycles
- build a tree only from resolved explicit edges
- apply turn selection, paging, counts, and ordering without hiding truncation
- return an empty valid envelope when no recognized child IDs exist
- prove participant output contains no prompts, messages, results, or tool output
- validate JSON, JSONL, and human output against the new schema contract

### Package tests

- include both new schemas in the package allowlist
- expose the new public APIs and schema names
- cover CLI dispatch and help for only `tail` and `participants`
- update version checks for `0.2.0`

## Subagent use

Luna High subagents may be used for bounded implementation or review work when
parallel work helps. No more than two Luna High subagents may run at once. The
root agent owns integration and assigns non-overlapping files or read-only
reviews.

## Done

V2 is ready when an agent can follow a stored thread through a bounded,
change-oriented stream and inspect its explicitly recorded subagent structure
without loading child transcript content or using experimental Codex methods.
